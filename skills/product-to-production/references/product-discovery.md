# Product Discovery

Read this reference for a greenfield product, a substantial new feature, or a request whose intended behavior is not yet concrete.

## Establish the product contract

Capture only what is necessary to make sound design decisions:

- problem and desired outcome;
- intended users and important actors;
- primary use cases and critical journeys;
- smallest useful release;
- explicit non-goals;
- observable acceptance criteria;
- business, regulatory, security, budget, schedule, platform, and deployment constraints;
- external services, data sources, and integrations;
- assumptions that need evidence.

Do not demand a full specification before learning can begin. Infer routine details from context and mark consequential assumptions clearly.

## Separate requirements from proposals

Distinguish:

- requirements the product must satisfy;
- constraints that cannot be changed within the task;
- current assumptions that should be tested;
- implementation proposals that remain replaceable;
- optional ideas that are outside the requested scope.

When a missing decision materially affects the data model, public contract, security model, user journey, cost, or long-term architecture, present a small number of viable options with benefits, costs, risks, and a recommendation.

## Define success

Prefer observable outcomes over vague quality labels. A useful acceptance criterion identifies the actor, action, expected result, and relevant failure behavior. Include non-happy paths when they change the design.
